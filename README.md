# Как создать Git-репозиторий и загрузить его на GitHub

### 1. Создать папку проекта и перейти в неё

```bash
mkdir my-project
cd my-project
```

### 2. Инициализировать Git-репозиторий

```bash
git init
```

### 3. Создать файлы проекта

Например, создать `README.md` и добавить в него описание проекта.

### 4. Добавить файлы в staging area

```bash
git add --all
```

### 5. Создать коммит

```bash
git commit -m "Initial commit"
```

### 6. Создать репозиторий на GitHub

- Открыть GitHub и нажать **New repository**.
- Указать название репозитория.
- Выбрать Public или Private.
- Не добавлять README, `.gitignore` и лицензию, если они уже есть локально.
- Нажать **Create repository**.

### 7. Связать локальный репозиторий с GitHub через SSH

Скопировать SSH-адрес репозитория на GitHub и выполнить:

```bash
git remote add origin git@github.com:USERNAME/REPOSITORY.git
```

### 8. Проверить подключение

```bash
git remote -v
```

### 9. Отправить коммит на GitHub

Проверить название текущей ветки:

```bash
git branch --show-current
```

Отправить ветку (если она называется `main`):

```bash
git push -u origin main
```

Если ветка называется `master`, использовать `master` вместо `main`.

## Как отправлять последующие изменения

После редактирования файлов:

```bash
git add --all
git commit -m "Describe changes"
git push
```

**Полезные команды:**

- `git status` — проверить состояние файлов.
- `git remote -v` — проверить адрес удалённого репозитория.
- `git log --oneline` — посмотреть историю коммитов.
# Git: статусы файлов, коммиты и HEAD

## 1. `git status`

Показывает состояние рабочей директории и области подготовки (`staging area`).

```bash
git status
git status --short  # сокращённый вывод
```

## 2. Жизненный цикл файла в Git

Основные состояния файла:

- **Untracked** — Git ещё не отслеживает файл.
- **Unmodified** — файл отслеживается, но не изменён относительно последнего коммита.
- **Modified** — файл изменён, но изменения ещё не добавлены в staging area.
- **Staged** — изменения добавлены в staging area и готовы к коммиту.

### Схема жизненного цикла

```text
          Создание файла
                 ↓
             Untracked
                 ↓ git add
               Staged
                 ↓ git commit
             Unmodified
                 ↓ редактирование
              Modified
                 ↓ git add
               Staged
                 ↓ git commit
             Unmodified
```

После изменения отслеживаемого файла его состояние становится `Modified`. Команда `git add` переносит текущие изменения в staging area. Если после этого снова отредактировать файл, он может одновременно содержать **Staged и Modified** изменения.

Удаление отслеживаемого файла тоже считается изменением: `git add` подготовит удаление к коммиту.

### Как читать `git status`

| Статус | Что означает |
|---|---|
| Untracked files | Новые, ещё не отслеживаемые файлы |
| Changes not staged for commit | Изменённые или удалённые файлы, изменения которых не подготовлены |
| Changes to be committed | Изменения, подготовленные к коммиту |
| Nothing to commit, working tree clean | Нет изменений относительно текущего коммита |

В сокращённом выводе `git status --short` используются два символа:

| Обозначение | Значение |
|---|---|
| `??` | Неотслеживаемый файл |
| ` M` | Файл изменён в рабочей директории |
| `M ` | Изменения файла добавлены в staging area |
| `MM` | Файл добавлен в staging, а затем снова изменён |
| `A ` | Новый файл подготовлен к коммиту |
| `D ` | Удаление подготовлено к коммиту |

Первый символ относится к staging area, второй — к рабочей директории.

## 3. Основные команды для работы с файлами

```bash
git add --all     # подготовить все изменения
git add file.py   # подготовить конкретный файл
git diff          # посмотреть изменения, не добавленные в staging
git diff --staged # посмотреть подготовленные изменения
git commit -m "Describe changes"  # создать коммит
```

## 4. Коммиты и их хеши

**Коммит** — зафиксированный снимок состояния проекта вместе с метаданными: автором, датой, сообщением и ссылками на родительские коммиты.

Каждый коммит имеет уникальный идентификатор — **хеш** (SHA-1 в обычной конфигурации Git).

```bash
git log                 # история коммитов
git log --oneline       # короткая история
git show HASH           # подробности конкретного коммита
```

Пример сокращённого хеша:

```text
a1b2c3d Add login tests
```

В командах обычно можно использовать сокращённый хеш, если он однозначно определяет нужный коммит.

## 5. Что такое HEAD

**HEAD** — указатель на текущую позицию в истории Git. Обычно он указывает на текущую ветку, а та — на последний коммит этой ветки.

Например:

```text
HEAD → main → последний коммит
```

При переключении ветки `HEAD` начинает указывать на другую ветку. В режиме detached HEAD он указывает непосредственно на коммит, а не на ветку.

## 6. Главное, что нужно запомнить

- `git add` — подготавливает изменения, но не сохраняет их в истории.
- `git commit` — фиксирует подготовленные изменения в истории.
- `git push` — отправляет коммиты в удалённый репозиторий.
- `git status` — помогает понять, что происходит с файлами прямо сейчас.
- Хеш идентифицирует конкретный коммит.
- `HEAD` показывает текущую позицию в истории Git.
